# OBS Music Widget Project Instructions

These instructions apply to the entire repository and document its development,
security, compatibility, and review constraints.

## Project Purpose

This project provides a locally hosted Spotify now-playing widget for OBS Studio.

The application consists of:

- A local Node.js server
- A browser-based configuration dashboard
- A transparent OBS browser-source widget
- Spotify authorization through Authorization Code with PKCE
- JSON-based configuration without a database
- Silent lifecycle integration with Streamer.bot

The project is intended for a single-PC streaming setup and should remain
lightweight while OBS and the game are running.

## Supported Environment

- Primary platform: Windows 10 and Windows 11
- Runtime: Node.js 22
- Package manager: npm
- Browser runtime: OBS Browser Source and current desktop browsers
- Default server address: `127.0.0.1:3847`

Do not add platform-specific behavior for another operating system unless the
user explicitly requests it.

## Technology Stack

- TypeScript for browser and server code
- Fastify for the local HTTP server
- React for the dashboard
- Preact for the OBS widget
- Vite for browser builds
- Zod for configuration validation
- WebSockets for live configuration and playback updates
- Windows DPAPI for Spotify token protection
- JSON for persistent configuration
- SCSS compiled by Vite for the dashboard and widget layouts

Do not replace these technologies or add another frontend, CSS, state-management,
database, or server framework without explicit approval.

Do not add Tailwind CSS or another CSS framework solely to fix an isolated
layout or styling problem.

## Configuration

The application must remain database-free.

Persistent configuration belongs in:

```text
.data/config.json
```

Requirements:

- Treat `src/shared/schema.ts` as the source of truth for configuration shape,
  defaults, migrations, and shared message types.
- Validate configuration with Zod before saving or using it.
- Keep configuration human-readable.
- Write configuration atomically.
- Preserve existing user configuration when adding fields.
- Add defaults or migrations for new fields.
- Do not silently discard a valid existing configuration.
- Do not store tokens, secrets, cached covers, or runtime control values in the
  normal configuration file.
- Do not include `.data/` content in source control, documentation examples, or
  test output.

## Secrets and Runtime Data

Spotify tokens are stored separately in:

```text
.data/spotify.tokens
```

On Windows, token data must remain protected with DPAPI for the current user.

The runtime descriptor is stored in:

```text
.data/runtime.json
```

It contains process information and the shutdown control token.

Requirements:

- Never expose Spotify access tokens, refresh tokens, authorization codes,
  PKCE verifiers, OAuth state values, or shutdown tokens to browser clients.
- Never place secrets in URLs, logs, screenshots, tests, or README examples.
- Preserve the single-instance server behavior.
- Remove stale runtime files when they are confirmed to reference a dead process.
- Keep shutdown graceful and close Spotify timers, WebSockets, HTTP listeners,
  and runtime files.
- Do not introduce plaintext token storage as a fallback on supported Windows
  systems.

## Local Server Boundary

The application is local by design.

- Keep the HTTP server bound to `127.0.0.1`.
- Do not bind to `0.0.0.0` or expose it to the LAN without explicit approval.
- Do not add cloud hosting, remote accounts, telemetry, or a hosted backend.
- Keep the shutdown endpoint protected by the runtime control token.
- Do not expose configuration mutation or shutdown controls to arbitrary
  external origins.
- CORS exceptions must be route-specific and justified.
- The health endpoint may remain accessible to the local `file://` OBS
  bootstrap.
- Keep the application usable without internet access except for Spotify and an
  explicitly selected Google Font.

## Spotify Authorization

Use Spotify's official Authorization Code flow with PKCE.

Requirements:

- Do not request or store a Spotify Client Secret.
- Generate a cryptographically random OAuth state.
- Generate a PKCE verifier and an S256 challenge.
- Expire pending authorization attempts.
- Use this exact default redirect URI:

```text
http://127.0.0.1:3847/api/auth/callback
```

- Do not replace `127.0.0.1` with `localhost`.
- Keep requested scopes limited to the current feature set.
- Do not add playback control scopes for metadata-only features.
- Refresh access tokens through Spotify's official token endpoint.
- Clear invalid tokens and request reauthorization when Spotify rejects a
  refresh token.
- Provide an actionable browser response after authorization succeeds, fails,
  expires, or is cancelled.
- Keep the dashboard setup instructions synchronized with the real redirect URI
  and authorization behavior.

Before changing scopes, artwork handling, attribution, playback behavior, or
Spotify branding, check Spotify's current official developer documentation and
policy.

## Spotify Playback Polling

The widget should represent pause, resume, and track changes promptly without
creating unnecessary load.

- Keep normal active playback polling near the existing 1.5-second interval
  unless a measured reason supports a change.
- Use a slower interval when no active playback exists.
- Follow Spotify's `Retry-After` header after HTTP 429 responses.
- Avoid overlapping playback requests.
- Refresh an expiring token before polling when necessary.
- Preserve a clear distinction between:
  - checking
  - ready
  - idle
  - not authorized
  - reauthorization required
  - rate limited
  - network or API error
- Broadcast meaningful state transitions to connected widget and dashboard
  clients.
- Do not fabricate playback data when Spotify is unavailable.

## Cover Handling

Supported cover modes are:

- `square`
- `none`

Do not add Canvas, Vinyl, cropped artwork, masks, holes, rotation, artwork
animation, distortion, overlays, or artwork blur without explicit approval and
a new review of Spotify's current content rules.

Artwork requirements:

- Display the artwork as supplied.
- Preserve its aspect ratio.
- Do not crop or modify the artwork.
- Cache the current cover only in server memory.
- Serve the cached cover locally to OBS.
- Keep the cover response size-limited.
- Validate that the upstream response is an image.
- Replace the cache when the source URL changes.
- Discard the cache when the server stops.

The cover tint feature may extract a representative color from the artwork and
apply it to the metadata panel. It must not blur or modify the artwork itself.

## Spotify Attribution

- Use the bundled official Spotify logo assets.
- Keep attribution visible whenever Spotify metadata is displayed.
- Link the attribution to the current item on Spotify.
- Do not place the Spotify logo over the album artwork.
- Keep attribution in its own metadata row where the layout provides one.
- Do not add the text `Provided by Spotify` unless current official policy
  requires it.
- Do not recolor, distort, animate, or recreate the Spotify logo.
- Keep light and dark logo variants local to the project.

## External Resources

Application assets should remain local by default.

Allowed external requests are limited to:

- `accounts.spotify.com` for authorization and token refresh
- `api.spotify.com` for playback metadata
- Spotify image CDN hosts for the current cover
- `open.spotify.com` after an explicit user click
- `fonts.google.com` after an explicit dashboard link click
- `fonts.googleapis.com` and `fonts.gstatic.com` only when a Google Font is
  actively selected

Requirements:

- Do not add CDNs for JavaScript, CSS, icons, or normal application fonts.
- Bundle application dependencies and normal assets locally.
- Do not add analytics, telemetry, error reporting, advertising, trackers, or
  remote configuration.
- Document any newly required host in the README before adding the request.
- Lazy-load optional external resources.
- Keep Inter and Poppins available as fully local fonts.

## Google Fonts

Google Fonts support must remain optional and must not require an API key.

- Let users find a font on the official Google Fonts website.
- Accept supported Google Fonts specimen or family URLs.
- Extract and store only the font-family name.
- Do not download or redistribute Google Font files.
- Load only the selected family at runtime.
- Do not request Google Fonts resources when a local font is selected.
- Fall back to the system sans-serif font if the selected Google Font cannot be
  loaded.
- Keep the dashboard privacy explanation accurate.

## Localization

Supported interface languages are:

- English
- German
- Browser-language automatic selection

Requirements:

- Store dashboard translations in:

```text
src/client/dashboard/locales/
```

- Store widget-status translations in:

```text
src/client/widget/locales/
```

- Keep English and German locale keys identical.
- Use English as the fallback for unsupported browser languages.

## Dashboard Behavior

- Configuration changes should update local state immediately.
- Persist normal changes through the existing short debounce.
- Use immediate saves for settings where delayed persistence would be confusing.
- Broadcast saved configuration to all connected widgets.
- Do not require the user to reset or refresh an OBS source after changing a
  setting.
- Keep Spotify setup collapsed when authorization is complete and no action is
  required.
- Open Spotify setup automatically when authorization is missing or expired.
- Preserve the language selector in the dashboard header.
- Keep controls, spacing, borders, icons, labels, and interaction states
  visually consistent.
- Use the existing SVG icon components instead of text characters for chevrons
  and interface icons.
- Avoid browser-native disclosure arrows when their appearance conflicts with
  the dashboard design.
- Keep the live preview fully visible and correctly scaled.
- Do not crop the preview.
- Organize desktop settings into accessible category tabs so the page itself
  stays fixed while the active settings pane scrolls.
- Show the recommended OBS source width, height, and frame rate for the selected
  layout.

## OBS Widget Behavior

The widget is a transparent browser source.

Requirements:

- Preserve transparent backgrounds on `html`, `body`, and the widget root.
- Do not add a full-source opaque background.
- Treat OBS Chromium behavior as part of the supported runtime.
- Avoid cross-origin iframe composition for the production OBS widget.
- Preserve live configuration and playback updates through WebSockets.
- Reconnect automatically after a WebSocket interruption.
- Do not require an OBS source reset.
- Show a localized status card when the server is unavailable, Spotify is not
  authorized, authorization has expired, Spotify is rate-limiting requests, or
  a relevant connection error occurs.
- Do not replace an actionable failure state with a blank widget.
- Keep the widget lightweight and avoid unnecessary rerenders, timers, and
  network requests.
- Preserve transparent padding needed for shadows and animations.

## OBS Bootstrap

The root `obs-bootstrap.html` is a standalone local-file source for OBS.

- It must work when the Node.js server is not running.
- It must keep the page background transparent.
- It should show a small localized server-not-running status card.
- It should retry the local health endpoint at a reasonable interval.
- After the health check succeeds, navigate the top-level browser source to the
  HTTP widget.
- Do not render the HTTP widget in a visible cross-origin iframe because OBS
  Chromium may composite it as an opaque surface.
- Keep the server address and widget route synchronized with the application
  defaults.
- Ensure `dist/obs-bootstrap.html` matches the root source after a build.

## Layouts and Source Dimensions

When changing layout geometry:

- Keep the dashboard preview dimensions synchronized.
- Keep the README table synchronized.
- Preserve enough transparent safety space for shadows and entrance or exit
  animations.
- Test both `square` and `none` cover modes.
- Test with and without the visualizer.

## Boxy Layout

- Keep the panels beside the cover equal in width.
- Keep the cover and adjacent panels visually aligned in height.
- Keep the current time left-aligned.
- Keep the duration right-aligned.
- Keep the duration right-aligned when the visualizer is disabled.
- Let the visualizer fill the space between both time values.
- Add more visualizer bars as space increases instead of increasing the gap
  between bars.
- Let the progress bar use the full inner width of its panel while respecting
  equal horizontal padding.
- Keep the time row aligned with the metadata title row.
- Keep the progress bar visually aligned with the Spotify attribution row.

## Minimal Layout

- Keep the layout on one visual line.
- Place the optional unmodified cover first, followed by title, separator,
  artist, progress, and Spotify attribution at the far edge.
- Keep title and artist at the same font size and give metadata the flexible
  share of the available width.
- Let a short title size to its content so the separator follows it; cap the
  title at half of the metadata width and give the artist the remaining space.
- Let the row consume the full safe browser-source width while its height
  controls proportional scaling.
- Cap the rendered row height at the size used within a 70 px source. Recommend
  a 100 px source so the additional height remains transparent safety room for
  shadows and transitions rather than scaling the row up.
- Keep the full Spotify logo in a dedicated, visually separated attribution
  zone at its required fixed rendered width.
- Omit time labels and the decorative visualizer in this layout.
- Let metadata use the released space when the cover is hidden.
- Preserve the existing long-metadata movement independently for title and
  artist.

## Long Metadata

Long titles and artist names should use the existing overflow movement.

- Wait approximately 10 seconds before movement starts.
- Move smoothly until the hidden end of the text is visible.
- Wait approximately 5 seconds at the end.
- Move smoothly back to the starting position.
- Do not animate text that already fits.
- Recalculate overflow after font, layout, viewport, title, or artist changes.
- Respect reduced-motion preferences where supported.
- Do not use a harsh marquee loop.

## Animations

Supported entrance and exit animation choices are:

- None
- Fade

Legacy Grow, Shrink, Swing, Tilt, and Slide values are migrated to Fade when
existing configuration is loaded.

Requirements:

- Keep entrance and exit selections independent.
- Keep animation duration readable rather than abrupt.
- Preserve the configured hide-on-pause and song-change-only behavior.
- Avoid clipping animated content at the OBS source boundary.
- Do not animate album artwork in ways that conflict with Spotify content
  requirements.
- Respect reduced-motion preferences for non-essential movement.

Chromagic uses Panel Cascade as its fixed palette transition. Do not expose a
palette-transition selector in the dashboard.

## Visualizer

The visualizer is decorative and does not represent real audio amplitude.

- Do not claim that it is synchronized to Spotify audio.
- Show it only during active playback.
- Keep bar spacing stable.
- Add or remove bars dynamically based on available width.
- Do not shift the time labels when the visualizer is disabled.
- Avoid expensive per-frame JavaScript.
- Prefer CSS animation for decorative movement.

## Styling

- Keep SCSS organized through the existing Atomic Design folders: abstracts,
  base, atoms, molecules, organisms, layouts, and utilities where applicable.
- Use Sass `@use`; do not introduce legacy Sass `@import` statements.
- Use shallow nesting for component-owned descendants, states, and pseudo-elements.
  Keep reusable classes independent and avoid nesting deeper than three levels.
- Keep generated CSS in the Vite build output rather than beside source SCSS.
- Reuse current tokens, spacing, radii, colors, shadows, and control patterns.
- Keep dashboard and widget styles separate.
- Do not add inline styles for static presentation when a CSS class fits.
- Use inline styles only for genuinely dynamic values such as runtime colors,
  dimensions, or transforms.
- Preserve dark and light themes.
- Verify text contrast over cover-derived colors.
- Cover tint must not change text color or shadow unless the per-profile
  automatic readability option is enabled.
- Keep manual text color and shadow values stored while automatic readability
  is enabled.
- Derive the unfilled progress-track color from the accent by default. Use the
  stored custom base color only when its per-profile switch is enabled; the
  accent continues to control progress fill and the visualizer.
- Use restrained text shadows only where dynamic backgrounds require them.
- Do not add animated glow effects to the cover tint feature.
- Avoid decorative Unicode in buttons, labels, and links.
- Use existing icon components for chevrons and external-link indicators.

## Accessibility

- Use semantic controls for buttons, links, labels, inputs, and selections.
- Preserve keyboard navigation and visible focus styles.
- Provide accessible names for icon-only controls.
- Keep collapse and expand state available through `aria-expanded`.
- Associate form guidance and errors with the relevant control.
- Do not use color alone to represent save, connection, warning, or error state.
- Keep interactive target sizes practical.
- Ensure dashboard controls remain usable at narrow widths and browser zoom.
- Keep status updates understandable without relying on animation.

## Performance

This project shares resources with OBS and the streamed game.

- Avoid unnecessary frontend frameworks and large runtime dependencies.
- Keep the OBS widget smaller than the dashboard when choosing dependencies.
- Prefer Preact-compatible code in the widget.
- Avoid high-frequency state updates unrelated to visible changes.
- Do not decode or process the same cover repeatedly.
- Avoid canvas rendering when CSS can provide the required decorative effect.
- Avoid continuous JavaScript animation loops.
- Clean up timers, observers, event listeners, WebSockets, and temporary DOM
  nodes.
- Measure before introducing caching or optimization complexity.
- Do not reduce Spotify polling below the current interval without considering
  rate limits and measured benefit.

## Streamer.bot Lifecycle

Streamer.bot should be able to start and stop the server without displaying a
console window.

- Keep `scripts/music-widget-background.vbs` as the silent Windows launcher.
- Resolve Node.js through the standard installation location or Windows PATH.
- Keep start, stop, and status behavior in the compiled server entry point.
- Do not require npm to remain running after startup.
- Do not open CMD, PowerShell, or a visible Node console window during silent
  startup.
- Keep Streamer.bot paths in documentation generic.
- Do not embed the developer's real project path in source or documentation.
- Preserve idempotent startup so duplicate start events do not create duplicate
  servers.
- Preserve graceful stop behavior.

## Testing Strategy

Keep automated testing proportionate to this local utility.

The required baseline is:

```powershell
npm test
```

The smoke test should cover:

- Server startup
- Health endpoint
- Health endpoint access from the local OBS bootstrap origin
- Configuration read and write
- Initial WebSocket snapshot
- Dashboard route
- Widget route
- Graceful shutdown

Add focused tests when changing:

- Configuration parsing or migration
- Google Fonts URL parsing
- Spotify response normalization
- OAuth state or PKCE behavior
- Retry or rate-limit handling
- Lifecycle and shutdown behavior
- Layout calculations that can be tested without visual duplication

Do not add a broad test framework for simple presentation-only changes.

For CSS or layout changes, verify the relevant dashboard preview and OBS-sized
widget state manually when browser tooling is available. Report visual checks
separately from automated tests.

Do not weaken shutdown, timing, or WebSocket assertions merely to hide a real
lifecycle problem.

## Local API

Preserve these routes unless an explicit API change is requested:

| Method | Route | Purpose |
|---|---|---|
| `GET` | `/api/health` | Local health and connection information |
| `GET` | `/api/config` | Read validated configuration |
| `PUT` | `/api/config` | Replace validated configuration |
| `GET` | `/api/playback` | Read normalized playback state |
| `GET` | `/api/cover/current` | Read the cached current cover |
| `GET` | `/api/auth/login` | Start Spotify authorization |
| `GET` | `/api/auth/callback` | Complete Spotify authorization |
| `POST` | `/api/auth/disconnect` | Remove stored Spotify authorization |
| `POST` | `/api/system/shutdown` | Stop the local process |
| WebSocket | `/ws` | Receive snapshots and live updates |

When adding or changing a route:

- Validate request input.
- Keep errors in English.
- Avoid exposing internal details.
- Update the README API table.
- Update the smoke test when the lifecycle contract changes.
- Preserve local-only security assumptions.

## Definition of Done

A change is complete when:

- The requested behavior is implemented.
- Existing unrelated behavior remains intact.
- Source and generated production output are synchronized.
- New user-facing text exists in English and German.
- Configuration changes include validation and migration defaults.
- Relevant README sections are current.
- `npm test` passes, or any inability to run it is reported precisely.
- No tokens, runtime data, personal paths, or unrelated changes were introduced.
- The final response states what changed, which checks ran, and any remaining
  user action or limitation.
